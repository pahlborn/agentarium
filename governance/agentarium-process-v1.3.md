# Agentarium Process 1.3
Revision: 2026-10-21. Peter authorized implementation of the agreed delivery improvements. Supersedes process 1.2 within Agentarium when integrated. Read Rulebook 1.3 and the exact task decision. No product publication, permission expansion, infrastructure activation or paid call is authorized by this revision.

## One outcome, one technical owner
Use direct work for a small low-risk task. For a technical task appoint one appropriately qualified owner for existing-system inspection, technical choice, implementation and own tests. Lot owns Agentarium visualization/interfaces; Forge owns other assigned architecture/development. Do not prescribe a second implementation or rename Lot as Forge. Atlas owns value, priority, delivery coordination and closure. Every member may challenge the plan and contribute; shared responsibility does not require every role on every task.

Use one independent checker for the decisive risk when independence is needed: Sentinel for executable behavior, Argus for assumptions/design/evidence. Add another role only for a distinct named risk or missing competence. Preserve required safety checks. Use Scout for a consequential factual gap, Nova for a material experience question and Archibald for material ambiguity. Do not force a full specification, universal QA ceremony or team vote on a routine change.

## 1. Before assigning consequential work
Atlas reads the current original task, implementation and outstanding replies. The technical owner confirms what already exists, the exact missing connection and the cheapest valid proof of the critical assumption before expansion.

Keep one compact task record, reusing the existing issue/PR: outcome; exact baseline; technical owner; scope/authority; decisive acceptance evidence/environment; next action/owner. Unknowns remain explicit. A small fix can fit in a few lines; it needs no new Epic, story set or full specification. Requirements cover applicable normal, failure and recovery behavior; new material scope returns to Peter.

Verify the receiving channel before dispatch. A subscribed PR, actual worker call or actual bridge receipt is evidence for its own context only. Record assignment before starting the worker when monitoring is selected. Host receipt is not worker start. Do not defer transition reporting until a final summary. Workers return their own evidence; a host may attest only transitions it actually observes, with provenance. Respect read-only roles' return-only limitations.

## 2. Prove the complete critical path early
For cross-system work, exercise one actual source-to-existing-product path before expanding status types, architecture or decoration. For Agentarium live work this includes a real task event reaching the intended consumer and the claimed visible effect. A queue counter or synthetic fixture is not a real rendered/device result. State what the selected environment can prove and what remains blocked.

The independent checker defines the smallest decisive normal/failure/recovery checks early when testability is a material risk. A test must distinguish the feared failure from success; inspect an appropriate counterexample or pre-fix behavior when feasible. Do not demand destructive production experiments. Reuse a proven browser runner rather than treating a missing local executable as absence of all test routes.

## 3. On each material handback or blocker
Atlas checks the exact result and relevant independently checked evidence, reconciles remaining criteria and assigns the next permitted action in the same work session. Do not wait for Peter to repeat an existing instruction. Reuse the task/finding ID; preserve dissent and failed history. Correct the issue and affected regressions, not the entire earlier pipeline.

An unreceived assignment remains unreceived. Inspect the actual run/channel once before retrying; do not busy-poll or spawn a duplicate. A repeated failed correction, unsupported success claim, recurring dropped handoff or drift without useful evidence triggers the learning step below. Continue unrelated safe work; keep an indispensable missing input blocked. A real execution or permission limitation must be named, not hidden by a plan.

## 4. Before saying complete
Atlas reconciles outcome, result, required checks, open findings and the applicable customer acceptance. A required failure is FAIL; required unavailable proof is BLOCKED. Acceptance is scoped to the exact artifact/environment. Component PASS does not become product PASS. Test evidence, accepted work, merge and publication are separate.

Integrate and verify an authorized governance/skill change; do not leave it as a draft merely because a future effectiveness check is pending. Product integration/publication follows its own authority. Report exact result, limits and any remaining owner/action. Do not promise unattended follow-up unless an authorized execution trigger actually exists.

## 5. Learn on a real trigger, not on Peter's reminder
All members report material process failures or repeatable improvements with original evidence. Atlas evaluates this at handback/blocker reconciliation and closure, not merely when Peter complains. Create or update one finding with: evidence; smallest correction; owner; status; next review event; effectiveness evidence. A deferred item needs a reason and a concrete next review event.

For recurring rework, repeated unsupported status, repeated routing failures or substantial scope/effort drift, Atlas routes one bounded original-evidence review to the real Cadence (`process-agent`) through an available authorized Claude host. Record published, received, started and returned separately when observed. No available route or paid authority: keep `pending_route` or `pending_authority`, name the exact missing prerequisite and continue safe work. Never simulate Cadence with another model or add a permanent poller, paid call or universal gate.

Cadence challenges Atlas as well as the team, proposes the smallest correction or no-change and names one later work event on which to check its effect. Atlas is responsible for arranging that follow-up, using an existing authorized callback when available. No callback means follow-up is pending, not promised automatic. Cadence cannot monitor between invocations. Material process changes are decided by Peter and Atlas; wording alone is not `verified_effective`.

## 6. Compare value with friction
After one bounded delivery, assess useful outcome and quality together with observed elapsed time, avoidable handoffs/questions, corrective iterations, Peter's required interventions and known costs. Reuse original records; do not create per-token telemetry or model calls for bookkeeping. Unrecorded time/cost remains unknown. Do not claim savings against an unmeasured solo baseline.

## Adoption and behavioral checks
Active task authority and safety boundaries take precedence. Existing sessions must actually reload the relevant changed definitions; a commit does not reload a running worker. Record independently checked role behavior separately from integration. Claude tools/model/effort limits remain unchanged. A clean-context dry run tests decision behavior only; a later actual task tests operational effectiveness.
